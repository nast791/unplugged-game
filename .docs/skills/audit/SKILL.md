# Аудит

## Когда брать

- перед сдачей системной правки: движок, генератор, контент-схемы, конфиг сборки, зависимости;
- закончен герой, экран или крупная часть партии;
- владелец просит «полный аудит» или «посмотри, что не так» перед merge.

## Главное правило

- **Чек-лист живёт в `.docs/rules/audit.mdc`**: скил его не переписывает и не сокращает — прочитать файл,
  идти по его разделам 1–8, здесь только порядок шагов и отчёт.
- **Сначала отчёт, потом правки.** По ходу проверки ничего не переписывается: находки собираются,
  показываются по критичности, правки — отдельными пачками после решения владельца.
- Замечание по неизменённому коду и «заодно переделать» в аудит не входят: предмет — дифф и то, что он
  задел.

## Порядок работы

1. **Границы диффа.** `git status --short`, `git diff`, `git diff --staged`: правка уже в индексе, без
   `--staged` её не видно. Каждый изменённый файл — в списке.
2. **Слои, которых коснулись.** `shared/` — движок и правила; `server/` — сборка партии, `view`, роуты
   Nitro; `app/` — клиент; `bot/` — политики и замеры; `tests/` — проверки; `server/content/` — карты,
   герои, пулы. Слои задают, какие разделы чек-листа и прогоны применимы.
3. **Пройти чек-лист `.docs/rules/audit.mdc`** по разделам: тесты, документация, мёртвый код, гварды,
   баги и логика, утечки, задуманная логика, «сломано / не работает». Пункт не применим к диффу —
   отметить это, а не молча пропустить.
4. **Сверить с картой:** новые действия, поля состояния, хуки и факты описаны в
   `.docs/rules/internal-logic.mdc` и `.docs/engine.md`; слой не поехал относительно
   `.docs/rules/architecture.mdc`.
5. **Прогнать проверки** по объёму диффа, а не «на всякий случай всё».
6. **Собрать отчёт** и ждать решения; правки после согласования — по приоритету, каждая со своим прогоном.

## Проверки

- Логика — тесты затронутых файлов, не весь набор:
  `node node_modules\vitest\vitest.mjs run tests/unit/core/immutability.test.js --pool=threads`.
- Системное (движок, генератор, контент-схемы, конфиг сборки, зависимости) — весь набор, фаззинг и сборка:

  ```powershell
  node node_modules\vitest\vitest.mjs run --pool=threads
  pnpm test:bot -- --seeds=2000
  node node_modules\nuxt\bin\nuxt.mjs build
  ```

- Клиент — только тронутая логика композаблов и `cn`; вёрстку агент не проверяет (`AGENTS.md` §6).
- Тронута документация — `pnpm docs:check`; пропуск проверки называется прямо, а не замалчивается.

## Отчёт

- находки по критичности, каждая с путём и строкой: **Critical / Should fix / Nice to have** (формат —
  `.docs/rules/audit.mdc`, «Отчёт»); для каждой — что не так и чем закрывается (тест, правка, решение);
- раздел чек-листа (1–8), который её выявил, — чтобы проверка не потерялась;
- что запущено (команда и итог), что нет и почему; правки — только после «делай».

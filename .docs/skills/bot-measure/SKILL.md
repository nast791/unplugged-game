# Замер бота

## Когда брать

- надо сравнить силу героев или политик, а не «посмотреть глазами»;
- вопрос владельца «партия тянется», «карта впустую», «бот застревает», «стало лучше?»;
- проверка правки бота (веса, признаки, оценка, условия карт), разбор находки фаззинга по сиду.

## Порядок работы

1. **Сформулировать вопрос и метрику до прогона.** «Политика X сильнее Y по винрейту», «медиана длины
   выросла», «доля эффектов без срабатывания упала». Без метрики прогон — числа без вывода.
2. **Выбрать инструмент по вопросу** (карта — `bot/README.md`, флаги — шапка каждого файла):

   | Вопрос                                           | Инструмент                                                                  |
   | ------------------------------------------------ | --------------------------------------------------------------------------- |
   | фаззинг пары: падения, тупики                    | `node bot/tools/run.js --seeds=200 --heroes=anubis,tesla`                   |
   | осмысленная политика, метрики                    | `$env:SEARCH_TIME='400'; node bot/tools/run.js --seeds=200 --policy=search` |
   | стол на 2–4 людей: проекция, битые клики         | `node bot/tools/hotseat.js --games=500`                                     |
   | матрица «все против всех» и метрики по героям    | `pnpm test:matrix -- --games=200 --policy=search`                           |
   | «партия тянется»: длина, истощение               | `node bot/tools/stall.js --games=40 --policy=search`                        |
   | «карта впустую»: эффект не сработал              | `node bot/tools/waste.js --games=60 --policy=search`                        |
   | где именно выигрывает политика, разрез по героям | `node bot/tools/stats.js --games=60 --workers=12 --policy=search`           |
   | проба одного хода с бюджетом времени             | `node bot/tools/think.js --time=1000 --samples=5`                           |

3. **Прогнать с явными `--games`/`--seeds`, `--from` и `--workers`** (`--workers=8` — обычный режим).
4. **Сравнить с базой.** Всё мерим живым ботом: `search` с выученным листом и `$env:SEARCH_TIME='400'`
   (`.docs/hero-balance.md` §5, §62–§63). `greedy` из замеров выведен (правило владельца, m00640),
   `random` — фаззинг, а не сила героя. Числа без базы не вывод.
5. **Сделать вывод с числами** и записать, каким сидом и какой политикой он получен. Переучивание бота,
   сводка побед по всем героям и рекомендации по коридору — скил `bot-balance`, а не этот.

## Правила замера

- **Одинаковые сиды** в сравниваемых сериях (`--from`, `--seed`), иначе разница — свойство сидов.
- **Не меньше партий, чем в шапке инструмента:** `run.js` — 60, `matrix.js` — 200, `stats.js` — 60,
  `waste.js`/`stall.js` — 40, `hotseat.js` — 60. Меньше — «дым», а не замер.
- **Лестницу мерить в обе стороны:** первый игрок сам по себе выигрывает 54–61%.
- **Бюджет и гены — в отчёт:** `SEARCH_TIME` (предел на решение, не на партию), `SEARCH_ITERATIONS`,
  `BOT_GENE_<ИМЯ>` меняют числа и ход игры; без них замер не воспроизводится.
- **Скрытое не читаем:** решения — по `runUi` и своим картам, чужое число атаки защитник считает
  ожиданием (`bot/play/counting.js`), иначе метрики нечестные (`.docs/pitfalls.md`).
- **Метрики:** доля побед, медиана длины партии, застревания (`stuck`/`noop`/`deadlock`), доля
  истощений, покрытие колоды (`.docs/hero-balance.md` §4–§5, §7); сбой (`crash`, `deadlock`, `invalid`,
  `view` — утечка проекции) разбирается по сиду, а не переигрывается «пока не позеленеет».

## Проверки

- Замер и есть проверка: прогон, серия, матрица; 40–60 партий — рабочий прогон, 500 — разбор.
- Тронул логику бота — прогон теста его файла:
  `node node_modules\vitest\vitest.mjs run tests/unit/bot/<файл> --pool=threads`.
- Весь набор, сборку и фаззинг по 2000 партий — только под системную проверку по просьбе владельца.

## Отчёт

- вопрос и метрика, команда целиком, сиды, число партий, политики, бюджет и гены; числа и база
  сравнения, вывод одной фразой, что не проверено и почему.

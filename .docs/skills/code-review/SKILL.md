# Ревью диффа

## Когда брать

- владелец просит «посмотри мою ветку», «отревьюй дифф», «что не так в правке»;
- перед merge крупной ветки или после большой правки движка;
- повторное ревью — когда правка переделана по прошлым замечаниям.

## Главное правило

- **Что считать дефектом — `.docs/review-rules.md`:** единственный источник (слои, блокеры, важное,
  «не является дефектом», формат). Скил его не пересказывает, а задаёт порядок шагов.
- **Что не читается построчно — `.docs/review-ignore.txt`.** Правило одной строки: есть в диффе хоть
  один файл вне списка — ревью полное; только файлы списка — построчное ревью не нужно, остаётся смысл.
- **Ревью — не правка:** не коммитить, не пушить, не стешить, не ребейзить, не править файлы. Находка —
  текст с путём и строкой, правит автор.
- **Только проблемы и как их решить:** похвалы, «это хорошо», «не критично» и замечания без действия
  в ревью не идут.

## Порядок работы

1. **Собрать дифф целиком:** `git diff` и `git diff --staged` — часть правок уже в индексе. Один файл —
   `git diff -- <путь>`, `git diff --staged -- <путь>`.
2. **Отсеять файлы по `.docs/review-ignore.txt`** до чтения, а не после; пропущенное в итог не пишется.
3. **Прочитать изменённые файлы целиком**, а не только патч; у изменённых функций найти вызывающих.
   Файлы вне диффа — только контекст, замечаний по ним нет.
4. **Пройти по слоям:** для каждого файла открыть правило его слоя (таблица «Слои и что в них смотреть» —
   `.docs/review-rules.md`) и сверить правку с инвариантами.
5. **Отделить дефект от шума** по разделу «Не является дефектом»: стиль проекта, вкусовые переносы,
   отсутствие теста на вёрстку и JSDoc — не находки.
6. **Написать замечания** по критичности: `файл:строка — что не так → что сделать`, метки `[блокер]` и
   `[важно]`. Один комментарий — один дефект; системная находка — один раз и списком строк.
7. **Сверить с текущей строкой диффа:** предлагаемая правка уже написана — находки нет.
8. **Отдать итог** в чат: что смотрел, блокеры, важное, «не дефект». Блокеров больше десяти — правка
   не готова.

## Что смотреть в проекте

| Что                                 | Файл                                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------- |
| Что считать дефектом, слои, формат  | `.docs/review-rules.md`                                                                         |
| Что не читается построчно           | `.docs/review-ignore.txt`                                                                       |
| Стиль — норма, а не находка         | `.docs/rules/code-style.mdc`                                                                    |
| Слои и папки                        | `.docs/rules/architecture.mdc`                                                                  |
| Движок, клиент, экран, карты, доска | `.docs/engine.md`, `.docs/ui.md`, `.docs/game-screen.md`, `.docs/cards-ui.md`, `.docs/board.md` |
| Бот                                 | `bot/README.md`                                                                                 |
| Грабли, что уже ломались            | `.docs/pitfalls.md`                                                                             |

## Запреты

- Не выдумывать дефекты из стиля и вкуса: переносы, кавычки, регистр, «читалось бы лучше» — шум.
- Не просить комментарии и JSDoc: в проекте они не поощряются и запрещены.
- Не писать гипотезы без проверки и не требовать «докажи прогоном»: прогоны — дело автора, зелёный
  прогон не аргумент против дефекта.
- Не трогать незавершённое, которое ждёт реализации: `TODO`, заглушки, моковые данные.

## Отчёт

- замечания по критичности в формате `файл:строка — что не так → что сделать`;
- для блокера — на какой инвариант или раздел правила опирается (путь и название, не пересказ);
- строка «что смотрел»: файлы, объём диффа, что отсеяно по списку; блок «не дефект» — что странно, но
  закреплено нормой.

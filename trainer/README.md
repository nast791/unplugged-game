# Универсальный тренер

Отдельный инструмент обучения: **правила не переписываются**. Игра остаётся в JS (`shared/`,
`server/content/`), тренер заказывает у неё партии и читает готовый контракт. Универсальность даёт не
вторая реализация движка, а **формат данных**: одна строка JSONL — одна точка решения.

```
trainer/
├── contract.py   # чтение JSONL, словари героев и карт, сводка выборки
├── model.py      # Q(state, action): эмбеддинги героев и карт, общий ствол, головы Q и V
├── train.py      # цикл обучения, сплит по партиям, метрики, артефакт
├── games.py      # обёртка над Node-поставщиком партий
└── artifacts/    # артефакты (JSON) — их читает JS-рантайм
```

## Зачем именно Q(state, action)

Шесть замеров подряд (`docs/hero-balance.md` §17–§21) показали одно и то же: оценка **позиции**
насыщена — признаки и точность растут, сила нет. Единственный непроверенный рычаг — оценивать пару
«состояние + действие», а для этого нужны градиенты, эмбеддинги и мини-батчи, то есть Python.

Цель обучения — не «правильный ход», а **доли доигрываний поиска** (дистилляция). Опыт проекта прямо
говорит, что учиться по винрейту плохо: покоординатный подбор весов дал +1 п.п. при шуме ±4,5% (§11),
а отдельные веса на пару героев — минус 2,6 п.п. точности (§20 C). Поиск знает больше, чем исход одной
партии, и передаёт это ученику.

Но дистилляция поиска **не сработала** (§24): на долях доигрываний ученик даёт 46% против `greedy`,
на жёсткой цели «повтори выбор учителя» (`--target=chosen`) — 48–50%, тогда как имитация ручной политики
даёт 51%. Причина не в учителе, а в цели и классе политики: поиск выбирает не по визитам (лидер по
визитам совпал с его выбором в 55% решений) и думает в детерминизированных мирах, а в дневник идёт
истинное состояние.

Обучение **на своих партиях** тоже не вышло (§26): цель `--target=self` (свой выбор, знак шага — исход) и
плотная цель «ценность хода» (`turn`) дали 4% против `greedy`; вариант без члена политики (только Q по
ценности хода, `--policy-weight=0`) — 29%. Знак исхода — не преимущество, а сама ценность: одна и та же
пара «состояние + действие» приходит в дневник и с плюсом, и с минусом, а исхода в признаках нет.
Вывод: двигать надо класс политики (MLP-рантайм) или использовать оценку **внутри** поиска, а не вместо
него. И ещё одно ограничение: numpy-тренер держит всю выборку в памяти — **1 млн точек не влезает**
(15 ГБ, своп), учиться нужно порциями (`--limit`).

## Контракт данных

Строка JSONL (пишет `bot/learn/export.js`):

| поле | что это |
| --- | --- |
| `v` | версия контракта (сейчас 1) |
| `game`, `step` | номер партии и шага: по `game` делится выборка |
| `player`, `rival` | кто решает и против кого (id героев) |
| `state` | признаки позиции глазами `player` (`bot/play/value.js`, 63 числа) |
| `winner` | исход партии или `null`, если не доиграна |
| `turn` | **ценность хода**: оценка позиции сразу после того, как ход `player` закончился (`null` — решение было в чужой ход или дневник старый) |
| `chosen` | индекс выбранного действия |
| `actions[]` | варианты: `key`, `card`, `prior` (вес политики), `visits` (доигрывания), `value` (ценность варианта от оракула, `--oracle`), `features` |

Признаки действия считаются **на стороне движка** (там есть карты, цели и клетки), тренер их не
интерпретирует — поэтому тот же тренер годится и для нового героя, и для другой игры с таким контрактом.
Заголовок несёт не только имена признаков: в поле `model` лежит отпечаток артефакта, которым играла
`qvalue` (`null` — дневник писала политика), поэтому по файлу видно, **какая версия** его написала.

Размерность признаков действия растёт вместе с признаками игры (сейчас **23**: у вариантов-клеток с §28
появились дистанция до ближайшего врага, «враг достаёт эту клетку» и дистанция до ближайшего своего бойца).
Расширение признаков **ломает совместимость**: в старых дневниках этих чисел нет, а старый артефакт
(`actionDim: 20`) грузится и играет, но новый блок не читает — дневник пересобирается, модель переучивается
(`trainer/data/oracle-c{1..4}.jsonl.gz` — дневник с признаками клетки).

## Запуск

Тренер не знает правил — партии заказывает у движка (`bot/learn/export.js`), поэтому Python нужен только
для обучения. На этой машине интерпретатор стоит не в PATH: `python` — заглушка Microsoft Store, рабочий
путь `%LOCALAPPDATA%\Programs\Python\Python314\python.exe`. Консоль Windows в cp1251, поэтому полезно
`$env:PYTHONUTF8=1` (скрипты и сами переключают stdout в UTF-8).

```powershell
$py = "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe"
& $py -m pip install numpy torch            # torch — для MLP-пути, numpy — для линейного

# 1. партии из движка (жадная самоигра дешёвая, поиск даёт мягкие цели политики)
node bot/learn/export.js --games=3000 --policy=greedy --out=trainer/data/greedy.jsonl.gz --gzip
node bot/learn/export.js --games=150  --policy=search --search-every=5 --out=trainer/data/search.jsonl.gz --gzip
node bot/learn/export.js --games=300  --policy=qvalue --out=trainer/data/self.jsonl.gz --gzip   # дневник ученика (§23)
node bot/learn/export.js --games=1500 --policy=qvalue --oracle=search --out=trainer/data/oracle.jsonl.gz --gzip  # свои партии, а ценность вариантов даёт поиск-оракул (§27)

# 2. проверка контракта (работает без torch) и обучение
& $py trainer/train.py  --data=trainer/data/greedy.jsonl.gz --check
& $py trainer/linear.py --data=trainer/data/greedy.jsonl.gz,trainer/data/search.jsonl.gz --epochs=8
& $py trainer/linear.py --data=trainer/data/search-a.jsonl.gz,trainer/data/search-b.jsonl.gz --target=chosen --q-weight=0 --value-weight=0  # жёсткая цель «повтори выбор учителя» (§24)
& $py trainer/train.py  --data=trainer/data/search.jsonl.gz --epochs=40   # нелинейный путь (MLP)
& $py trainer/train.py  --data=trainer/data/oracle-a.jsonl.gz,trainer/data/oracle-b.jsonl.gz --epochs=8 --target=oracle  # MLP на ценности вариантов (§28)

# 3. замер: обученная политика против эталонов
node bot/tools/matrix.js --policy=qvalue --policy-b=greedy --games=10 --workers=12
node bot/tools/matrix.js --policy=qvalue --policy-b=search --games=10 --workers=12
```

Два тренера дают **один и тот же формат артефакта**, но разное качество и разный рантайм:

| тренер | модель | когда брать | рантайм в игре |
| --- | --- | --- | --- |
| `linear.py` (numpy) | линейная Q со скрещиванием «позиция × действие» | работает всегда, весит 5 КБ, читается `bot/play/qvalue.js` | **да** (`--policy=qvalue`) |
| `train.py` (torch) | MLP с эмбеддингами героев и карт | когда нужна нелинейность; артефакт 110 КБ, тоже читается `qvalue.js` (§28) | **да**, но силу не поднял |

Артефакт, уже лежащий в `trainer/artifacts/`, возвращается в игру (в зеркало для бандла) без
переобучения: `& $py trainer/mirror.py --artifact=trainer/artifacts/mlp-q.json`.

Приёмка артефакта — не точность, а лестница: `--policy=qvalue --policy-b=greedy` и
`--policy=qvalue --policy-b=search` на 600 партиях. Если обученная политика не бьёт хотя бы `greedy`,
артефакт не берём. Полезны и флаги выбора цели: `--target=auto` (по умолчанию: доли доигрываний, иначе
веса политики), `--target=chosen` (жёсткая цель «повтори выбор учителя»), `--target=self` (свой выбор,
знак шага — исход партии или ценность хода, §26); `--q-weight=0 --value-weight=0` отключают регрессию на
исход — так видно, что даёт именно имитация учителя, `--policy-weight=0` — что даёт только оценка.

## Формат артефакта и forward-pass

Артефакт — только числа и словари, без torch, поэтому его читает JS (`bot/play/qvalue.js`):

```json
{ "kind": "mlp-q", "stateDim": 63, "actionDim": 23, "hidden": 64, "embed": 8,
  "heroes": [...], "cards": [...], "heroEmbed": [[...]], "cardEmbed": [[...]],
  "W1": [...], "b1": [...], "W2": [...], "b2": [...],
  "Wscore": [...], "bscore": [...], "Wvalue": [...], "bvalue": [...], "meta": {...} }
```

Матрицы лежат **по строкам** (`W1[i]` — строка `i`), forward-pass:

```
x  = [ state ⊕ actionFeatures ⊕ heroEmbed[player] ⊕ heroEmbed[rival] ⊕ cardEmbed[card] ]
h  = relu(W1 · x + b1),  h = relu(W2 · h + b2)
Q  = Wscore · h + bscore            # оценка пары «состояние + действие»
V  = Wvalue · state + bvalue        # оценка позиции (запасной сигнал)
```

Эти же формулы повторены в JS-рантайме (`bot/play/qvalue.js: mlpScore`), и совпадение проверено
на одном артефакте: те же 81 вариант хода посчитаны torch и JS — расхождение **1,1·10⁻⁷** (округление
весов при экспорте). Формулы закрыты и юнит-тестом с посчитанными вручную числами
(`tests/unit/bot/qvalue.test.js`).

### Две головы по виду решения (`--two-heads`, §49) — проверено, не берём

Природа решений разная: на картах согласие модели с целью 53–75%, на клетках до признаков клетки было 0%
(§28, §44). Флаг `--two-heads` даёт **два ствола и две головы**: шаги (клетки) считает своя пара
«ствол + выход», а карты, добор, бойцы и «закончить» — общая. Параметров столько же, сколько у одной
головы (это не «больше чисел», а другой набор признаков на входе), а второй ствол стартует **копией**
первого — чтобы разницу давало обучение, а не инициализация.

В артефакт уезжают `twoHeads: true` и веса `W1Cell`, `b1Cell`, `W2Cell`, `b2Cell`, `WscoreCell`,
`bscoreCell`; маршрут — признак 3 вектора действия («это клетка»), тот же, по которому делит тренер:

```powershell
& $py trainer/train.py --data=trainer/data/diary-e.jsonl.gz --epochs=8 --target=oracle `
  --two-heads --out=trainer/artifacts/mlp-two-heads.json --js-out=.workbuddy/mlp-two-heads.weights.js
```

**Числа (§49):** на удержанных партиях метрики неразличимы с живой моделью (`top-1` 64,8% против 65,0%,
знак Q 78,2% против 78,6%); лестница против `greedy` на 900 партиях — **55% против 53%** у контроля,
то есть **+2 п.п. в пределах шума (±3,3 п.п.)**, при вдвое более тяжёлом артефакте (216 КБ против 115 КБ).
В игру не пошло, живым остаётся `mlp-e2`; рантайм читает артефакт без голов как раньше. Тест маршрута —
`tests/unit/bot/two-heads.test.js`.

### Нелинейность «состояние × действие» (`--gated`, §50) — проверено, не берём

У линейной модели скрещивание задано руками (`wCross`), а у сети взаимодействие живёт только внутри
первого слоя — значит оно **общее**: один вес решает, «важен ли этот признак действия вообще», для всех
позиций. Флаг `--gated` делает взаимодействие **своим для каждой позиции**: вектор варианта умножается на
ворота из сводки позиции, `a' = a · σ(G · summary + g0)` (207 добавленных параметров).

```powershell
& $py trainer/train.py --data=trainer/data/diary-e.jsonl.gz --epochs=8 --target=oracle `
  --gated --out=trainer/artifacts/mlp-gated.json --js-out=.workbuddy/mlp-gated.weights.js
```

Артефакт уносит `gated`, `summaryIndex`, `summaryFeatures`, `Wgate`, `bgate`; рантайм
(`bot/play/qvalue.js: mlpScore`) считает ту же формулу. При нулевых весах ворот σ(0) = 0,5 — общая
половинная шкала действий, то есть старт эквивалентен прежнему поведению (закрыто тестом).

**Числа (§50):** `top-1` 65,1% и знак Q 78,4% на удержанных (у живой модели 65,0%/78,6%); против `greedy`
ворота дают 54% — столько же, сколько живая модель; прямой матч ворот против `mlp-e2` — **51% против 49%**
на 900 партиях и **51% против 49%** на 2 400 (1 215/1 185, шум ±2,0 п.п., порог круга «≥1000 партий»);
`rank.js` на честном дневнике — лучший вариант 45,2% против 45,1%, согласие 47,4% против 47,3%,
сожаление одинаковое. В игру не пошло, живым остаётся `mlp-e2`.
**Итог класса модели:** приор (§47), две головы (§49) и нелинейность (§50) — три разных механизма,
все дали паритет; упирается в цель и объём, а не в способ применения модели.

## Две версии лицом к лицу (матч артефактов)

Артефакт — **параметр**, а не константа (`bot/play/artifact.js`): у каждой стороны партии может быть свой
файл. Это то, что делает возможным приёмку без общего эталона и самоигру «ученик против ученика»:

```powershell
# слепок живого артефакта (чтобы матч был повторяем) — trainer/artifacts/mlp-live-c.json
node bot/tools/matrix.js --policy=qvalue --policy-b=qvalue `
  --artifact=trainer/artifacts/mlp-live-c.json --artifact-b=trainer/artifacts/mlp-d.json `
  --games=500 --from=30001 --workers=8

# то же с разрезом по героям: ученик за одного героя против ученика за другого
node bot/tools/stats.js --games=60 --workers=8 --policy=qvalue --policy-b=qvalue `
  --artifact=trainer/artifacts/mlp-d.json

# дневник такой самоигры (в заголовок уезжают и отпечаток модели, и имена артефактов)
node bot/learn/export.js --games=300 --policy=qvalue `
  --artifact=trainer/artifacts/mlp-live-c.json --artifact-b=trainer/artifacts/mlp-d.json `
  --out=trainer/data/selfplay.jsonl.gz --gzip
```

Читается так: «лестница в обе стороны» показывает винрейт **держателя `--artifact`** против держателя
`--artifact-b` (место первого хода взаимно сокращается, артефакты меняются местами в зеркальной партии).
Переменные среды `SEARCH_ARTIFACT`/`PLAN_ARTIFACT` делают то же самое для политик с поиском.

## Рефлексия: учиться на своих ошибках — проверено, не берём

`trainer/train.py --reflect=<λ>` взвешивает решения по величине ошибки: `вес = 1 + потеря/0,2 +
0,6·неуверенность`, где потеря — ценность лучшего варианта минус ценность сыгранного (по оценкам учителя
в дневнике). Замер схемы: медиана веса 1,58, максимум 10,97, вес >4 у 1,8% решений.

**Результат (сиды 20001…20500, по 500 партий на пару, лестница в обе стороны):** артефакт с рефлексией
проиграл живому **49% против 51%**, контрольный артефакт (тот же дневник, те же сиды, без рефлексии) —
50/50 и 54% против `greedy` (как живой). То есть взвешивание по ошибке **вредит**: оно усиливает решения,
где метка учителя шумная (ценности оракула на клетках согласованы сами с собой на 56–60%), и модель
подгоняет шум. Живым остаётся прежний артефакт; см. §45 в `AGENTS.md`.

## Честный оракул: парная оценка и геометрия — проверено, не берём

`bot/learn/export.js --oracle-paired --oracle-eval=position` считает ценность всех вариантов в **одних и
тех же** мирах (`pairedRootValues`) вместо «каждый вариант в своём», плюс лист с геометрией. Идея — убрать
шум меток: на клетках оракул согласен сам с собой лишь на 56–60% (§29).

**Числа (§46).** Цена: **8,7× дороже** обычного при том же бюджете (240 партий: 337 с против 2 940 с).
Качество меток: **самоконтроль оракула** (тот же вопрос дважды с разными зёрнами, 204 решения) —
обычный согласен сам с собой на **50,0%** по лучшему варианту и 63,0% по парам, честный — на **64,7%** и
**78,8%**: шум меток действительно падает вдвое. Но сила игры от этого **не растёт**: на 240 партиях
честные метки 52% против `greedy`, обычные 53%; на 760 партиях **обе по 53%**, лицом к лицу 50/50,
против живого артефакта 49% и 50%. На удержанных партиях `top-1` у честных меток ниже (47,5% против 62,5%)
именно потому, что они меньше шумят.

**Вывод:** шум меток — не узкое место. Ни поиск как учитель, ни честные метки, ни объём не пробивают
53–54%: упирается в класс модели и признаки, а не в качество цели. Инструменты для проверки любого
следующего способа разметки: `--oracle-paired`/`--oracle-eval`, `.workbuddy/label-compare.mjs`,
`.workbuddy/oracle-selfcheck.mjs`.

## Границы

- Тренер не знает правил и не симулирует — если понадобится второй движок, это будет другая игра
  и другие веса.
- Артефакт должен остаться маленьким: он уезжает в браузерный бандл, а `vs_ai` считает ход в бюджете
  200 мс. Сеть на 175 тысячах точек весит **110 КБ**, веса кладутся в `Float64Array` — счёт идёт
  микросекунды, но за размером стоит следить (`trainer/train.py` печатает КБ).
- На машине разработчика Python может быть не установлен: тогда тот же контракт и тот же алгоритм
  можно прогнать JS-прототипом (`bot/learn/qnet.js`) — он пишет артефакт в этом же формате.

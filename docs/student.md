# Ученик: как он учится и как играет

Это описание одного механизма целиком — от «сыграли партию» до «бот сходил в браузере». Правила игры
здесь не переписываются: партии играет движок (`shared/`), тренер только читает готовые точки решения
(`bot/learn/export.js` → JSONL → `trainer/`). Ученик — это **артефакт** (числа и словари) плюс код,
который его читает (`bot/play/qvalue.js`).

Живая конфигурация: `bot/play/qvalue-weights.js` — зеркало `trainer/artifacts/mlp-q.json` (нелинейная
сеть, `kind: "mlp-q"`). Линейный артефакт сохранён кандидатом (`trainer/artifacts/q-linear.json`) и
возвращается в игру одной командой без переобучения.

---

## 1. Конвейер целиком

```
   ┌─────────────────────────── JS: правила и партии ───────────────────────────┐
   │ bot/play/duel.js   играет партию политикой (greedy | search | qvalue | …)  │
   │ bot/play/decide.js перечисляет варианты хода с весами политики             │
   │ bot/play/actionFeatures.js  23 числа на вариант (общий модуль с игрой!)    │
   │ bot/play/value.js           63 числа на позицию                            │
   │ bot/learn/export.js  ──►  JSONL: одна строка = одна точка решения          │
   └────────────────────────────────────┬───────────────────────────────────────┘
                                        │  trainer/data/*.jsonl.gz
   ┌────────────────────────────────────▼───────────────────────────────────────┐
   │ Python: trainer/contract.py читает контракт, trainer/linear.py (numpy) или │
   │ trainer/train.py (torch, MLP с эмбеддингами героев и карт)                 │
   │      ──►  trainer/artifacts/*.json  (5 КБ линейная, ~110 КБ сеть)          │
   └────────────────────────────────────┬───────────────────────────────────────┘
                                        │  trainer/mirror.py (или --js-out обучения)
   ┌────────────────────────────────────▼───────────────────────────────────────┐
   │ Игра: bot/play/qvalue-weights.js  →  bot/play/qvalue.js                    │
   │   политика `qvalue`  — ученик решает сам                                   │
   │   политика `qprior`  — ученик подсказывает поиску (приор корня)            │
   │   vs_ai в браузере   — bot/play/ai.js: поиск с лимитом времени             │
   └────────────────────────────────────┬───────────────────────────────────────┘
                                        │
              замер: bot/tools/matrix.js (лестница в обе стороны)
              разбор: bot/tools/rank.js  (согласие, сожаление, разрезы)
                                        │
                                        └──►  следующий круг: снова партии
```

Круг замкнут: каждый замер объясняется разбором, а разбор говорит, что менять — дневник, цель, признаки
или класс модели. **Круг самообучения — постоянный** (`TODO`, пункт «Круг самообучения»).

## 2. Шаг 1. Партии и дневник

### Кто играет партии

```powershell
node bot/learn/export.js --games=1000 --policy=qvalue --oracle=search --out=trainer/data/oracle-c.jsonl.gz --gzip
```

- `--policy` — **кто играет партии**: `greedy` (ручная политика), `search` (поиск), `qvalue` (сам ученик),
  `qprior` (поиск с подсказкой ученика). Это и есть ответ на вопрос «на чьих решениях он учится».
- `--policy-b` — политика второй стороны (по умолчанию та же).
- `--oracle=search` — **критик**: на каждом решении запускается поиск и считает ценность **всех** вариантов
  (`value`), а не только сыгранного. Это то, что позволяет учиться «какой ход был бы лучше», а не «этот
  ход вышел удачным».
- `--heroes=a,b` — ограничить пул; `--from=…` — с каких сидов; `--search-every=N` — прореживать дорогие
  решения, если партии играет поиск.
- Герои чередуются по номеру партии (`heroes[i % n]` против `heroes[(i+1) % n]`), сид партии = `from + i`,
  поэтому **тот же набор сидов воспроизводится** при повторном запуске.

### Что попадает в файл

Первая строка — заголовок:

| поле                          | что это                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| `baseFeatures`                | 63 имени признаков позиции, порядок задаёт `bot/play/value.js`                         |
| `summaryFeatures`             | 8 имён «сводки» — те признаки позиции, которые модель скрещивает с признаками действия |
| `actionFeatureDim`            | длина вектора признаков действия (**23**)                                              |
| `heroes`, `policy`, `policyB` | пул героев и политики сторон                                                           |
| `model`                       | **отпечаток артефакта**, которым играла `qvalue` (`null` — играла ручная политика)     |
| `turnValue`, `oracle`         | есть ли ценность хода и кто был критиком                                               |

Отпечаток модели нужен, чтобы по дневнику было видно, **какая версия** его написала: сравнивать потом
нужно именно с ней.

Каждая следующая строка — точка решения:

| поле                | что это                                                                       |
| ------------------- | ----------------------------------------------------------------------------- |
| `v`, `game`, `step` | версия контракта, номер партии, номер шага (по `game` делится выборка)        |
| `player`, `rival`   | кто решает и против какого героя                                              |
| `state`             | 63 числа: позиция глазами `player`                                            |
| `actions[]`         | варианты: `key`, `card`, `prior`, `visits`, `value`, `features`               |
| `chosen`            | индекс сыгранного варианта в `actions[]`                                      |
| `turn`              | **ценность хода**: оценка позиции сразу после того, как ход игрока закончился |
| `winner`            | исход партии (`null`, если партия не доиграна; дописывается в конце)          |

Смысл полей варианта:

- `prior` — вес варианта у **предлагающей** политики (нормирован на сильнейший в решении). Ученик видит
  не только «что можно», но и «что думает политика»;
- `visits` — доли доигрываний поиска (когда партию играет поисковая политика; иначе нули). Это цель
  дистилляции — и она **не сработала** (§24);
- `value` — ценность варианта от оракула (`--oracle`): главная цель сегодняшнего ученика;
- `features` — 23 числа признаков действия;
- `chosen` — сыгранный вариант. Ошибка в нём стоила круга обучения: `onStep` отдаёт действие вместе с
  `playerId`, а экспорт сравнивал список вариантов с полным payload — `chosen` молча становился нулём, и
  «ученик всегда выбирает первый вариант» не было видно ни в логе, ни в тесте (§23).

### Признаки действия (23 числа)

Считает **тот же модуль, что и в игре** (`bot/play/actionFeatures.js`) — поэтому расхождений «учили не
на том, на чём играют» быть не может. Порядок:

| индексы | смысл                                                                                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------- |
| 0..4    | вид действия: карта, колода (добор), боец (цель), клетка, «закончить»                                                 |
| 5..6    | сила карты / 10, усиление / 4                                                                                         |
| 7..9    | тип карты: атака или гибрид, защита или гибрид, эффект                                                                |
| 10..11  | обещание карты: эффективное число / 10 и прочая польза / 2 (`bot/play/cards.js: cardPromise`)                         |
| 12..13  | привязка карты: своему герою, помощнику                                                                               |
| 14..16  | цель-боец: здоровье / 16, это герой, дистанция до ближайшего врага / 6                                                |
| 17      | клетка: своя стихия героя                                                                                             |
| 18      | карта несёт метку ресурса героя (топливо: осколки, катушки, пелена)                                                   |
| 19      | вес политики для этого варианта, нормированный на сильнейший в решении                                                |
| 20..22  | клетка: дистанция до ближайшего врага / 6, враг достаёт её своей дальностью, дистанция до ближайшего своего бойца / 6 |

Блок 20..22 добавлен последним (§28). До него у вариантов-клеток внутри одного решения совпадали
**все** признаки (стихия и вес у них одинаковы), и **86,7%** таких решений получали одну и ту же оценку:
для модели «шаг к врагу» и «шаг в пустоту» были неразличимы, а у Медузы (три гарпии плюс герой) таких
решений больше всех. Старые артефакты (`actionDim: 20`) этот блок просто не читают — поэтому после
расширения признаков дневник пересобирается, а модель переучивается.

### Чего в дневнике нет

- **чужих карт**: варианты и признаки собираются по `runUi` (то, что движок показывает игроку), чужая
  рука в поиске сэмплируется из остатка колоды (`bot/play/counting.js`);
- **исхода в признаках**: исход — это цель, а не вход. Именно из-за этого «свой выбор × исход» не
  сработал (§26): одна и та же пара «состояние + действие» приходила в дневник и с плюсом, и с минусом.

## 3. Шаг 2. Обучение (Python)

Проверка контракта (работает без torch):

```powershell
$py = "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe"
& $py trainer/train.py --data=trainer/data/oracle-c.jsonl.gz --check
```

### Сплит

Делится **по номерам партий** (`--holdout=0.1`): строки одной партии не попадают и в обучение, и в
проверку. Иначе модель «узнаёт» партию, а не позицию, и метрики на удержанном врут.

### Цель (`--target`)

| цель         | что значит                                                      | итог                              |
| ------------ | --------------------------------------------------------------- | --------------------------------- |
| `auto`       | доли доигрываний `visits`, а где их нет — веса политики `prior` | 46% против `greedy` (§24)         |
| `chosen`     | «повтори выбор учителя» одним вариантом                         | 48–50%                            |
| `self`       | свой выбор, знак шага — исход партии или ценность хода          | 4% (29% без члена политики) (§26) |
| **`oracle`** | мягкое ранжирование по **ценности каждого варианта** от оракула | 50% против `greedy`, 51% на 1200  |

Цель `oracle` размазывается softmax по разбросу цен **внутри решения** (`--oracle-temperature=0.25`):
абсолютный уровень ценности — свойство позиции, а не выбора.

### Потери

```
loss = policy_weight · CE( softmax(Q(s,a)), цель ) · sign
     + q_weight      · MSE( Q(s, сыгранное a), исход )
     + value_weight  · MSE( V(s), исход )
```

`sign` = исход только для цели `self` (иначе 1). `--policy-weight=0` оставляет только регрессию, так
видно, что даёт оценка без имитации.

### Два тренера — один формат артефакта

|               | `trainer/linear.py` (numpy)                                       | `trainer/train.py` (torch)                                                                                                        |
| ------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| модель        | линейная Q со скрещиванием «позиция × действие»                   | MLP: `[состояние ⊕ действие ⊕ герой ⊕ соперник ⊕ карта]`, два слоя `relu` (`--hidden=64`), эмбеддинги героев и карт (`--embed=8`) |
| вид артефакта | `linear-q`, 5 КБ                                                  | `mlp-q`, ~110 КБ                                                                                                                  |
| когда брать   | работает всегда, считается за микросекунды                        | когда нужна нелинейность                                                                                                          |
| команды       | `& $py trainer/linear.py --data=… --target=oracle`                | `& $py trainer/train.py --data=… --epochs=8 --target=oracle`                                                                      |
| память        | держит всю выборку: **1 млн точек не влезает** → `--limit=400000` | мини-батчи, ограничения нет                                                                                                       |

Полезные флаги обоих: `--data=a.gz,b.gz` (несколько файлов через запятую), `--epochs`, `--lr`, `--limit`,
`--seed`, `--holdout`, `--out`, `--js-out`.

### Метрики обучения и как их читать

Печатаются каждые 5 эпох: **top-1 политики** (доля решений, где лучший по модели вариант совпал с лучшим
по цели), **знак Q** (у сыгранного варианта верный знак исхода), **MSE** регрессии.

Читать их надо трезво: top-1 на цели `oracle` вырос с 47,3% (линейная) до **61,0%** (сеть), а по парам
согласие осталось 49,4% при монетке 50,1% (§28). Точность цели и **сила** — разные числа; приёмка идёт
только лестницей (шаг 5).

### Осторожно: обучение само перезаписывает живой артефакт

`--js-out` по умолчанию равен `bot/play/qvalue-weights.js`, то есть **игра начинает читать новую модель
сразу после обучения**. Прошлый артефакт при этом остаётся в `trainer/artifacts/` — им и возвращают игру
назад:

```powershell
& $py trainer/mirror.py --artifact=trainer/artifacts/mlp-q.json   # вернуть прежнюю версию без переобучения
```

Поэтому порядок такой: **сначала** убедиться, что старый артефакт сохранён в `trainer/artifacts/`,
потом учить (лучше с `--out=trainer/artifacts/<новая-версия>.json`), потом мерить, и только по замеру
решать, оставлять ли новую версию живой.

## 4. Шаг 3. Артефакт

Артефакт — только числа и словари, без torch и без Python, поэтому его читает JS:

```json
{ "kind": "mlp-q", "stateDim": 63, "actionDim": 23, "hidden": 64, "embed": 8,
  "heroes": [...], "cards": [...], "summaryFeatures": [...], "summaryIndex": [...],
  "heroEmbed": [[...]], "cardEmbed": [[...]],
  "W1": [...], "b1": [...], "W2": [...], "b2": [...],
  "Wscore": [...], "bscore": [...], "Wvalue": [...], "bvalue": [...],
  "meta": { "samples": ..., "target": "oracle", "policy_top1": ... } }
```

Матрицы лежат по строкам, forward-pass:

```
x = [ state ⊕ actionFeatures ⊕ heroEmbed[player] ⊕ heroEmbed[rival] ⊕ cardEmbed[card] ]
h = relu(W1 · x + b1);  h = relu(W2 · h + b2)
Q = Wscore · h + bscore        # оценка пары «состояние + действие»
V = Wvalue · state + bvalue    # оценка позиции (запасной сигнал)
```

Те же формулы повторены в JS (`bot/play/qvalue.js: mlpScore`) и сверены с torch на одних и тех же 81
варианте: расхождение **1,1·10⁻⁷** (округление весов при экспорте). Формулы закрыты и юнит-тестом с
посчитанными вручную числами (`tests/unit/bot/qvalue.test.js`).

## 5. Шаг 4. Как ученик играет

### `qvalue` — ученик решает сам

1. `bot/play/decide.js: actionsFor(state, playerId, { policy: 'qvalue' })` перечисляет варианты хода
   **предлагателем рантайма** (`PROPOSER_POLICY`, сейчас `trade` — тот же, что перечисляет живой ход в
   браузере). Список не должен зависеть от модели (иначе модель сама себе сужает выбор), но обязан
   совпадать с живой игрой: признак 19 вектора варианта — это вес предлагателя, и по нему же считается
   veto. Раньше здесь стоял жадный предлагатель, и дневник учил ученика на весах политики, которых в
   игре нет (§23, `tests/unit/bot/proposer.test.js`);
2. `bot/play/qvalue.js: scoreOptions` считает `Q(s, a)` для каждого предложенного варианта;
3. `rankOptions` переставляет веса: softmax с температурой `SELECTION_TEMPERATURE = 0.25` (переменная
   среды `QVALUE_TEMPERATURE=0` — чистый argmax, так проверяют саму оценку);
4. **вес 0 — это veto, а не «мало»**: вариант, который политика запретила (шаг в никуда, добор на пустой
   колоде), модель не может вернуть — иначе бот топчется (лечили в §10, поймали в §22);
5. **примесь мнения политики** (`PRIOR_MIX = 0.8`): к оценке модели добавляется нормированный
   `log1p(веса)` политики. Появилась по замеру §29: на решениях-клетках цель (ценности оракула) шумная —
   оракул согласен сам с собой лишь на 56–60%, на картах 74–81%, — поэтому там, где модель не различает
   варианты, решает политика с ручными правилами движения, а не первый вариант списка. **Перемер §43**
   (по 14 400 партий на значение, свежие удержанные сиды): 0 — 51%, 0,15 — 53%, 0,3 — 53–54%, 0,6–3,0 —
   **55–56%**, 6,0 и 10,0 — 54%. То есть правила политики на текущем артефакте сильнее модели в её
   области, и оптимум примеси — около единицы; живое значение поднято с 0,3 до **0,8** (+2 п.п.).
   Переопределяется `QVALUE_PRIOR_MIX`. Отдельный механизм неуверенности (`UNCERTAIN_MIX` — примесь
   растёт там, где оценки модели совпали) добавлен, но при поднятой базовой примеси вклада не даёт.

Выбор действия дальше — взвешенный случайный по весам, поэтому у ученика есть температурная случайность
(это же делает возможным фаззинг и разнообразие партий).

### `qprior` — ученик подсказывает, а решает поиск

`searchAction` получает приор корня из оценок ученика (`rootPriors`, `priorSource: 'qvalue'`): лог-вероятности
softmax с той же температурой. Доигрывания остаются за поиском. Исторически это **единственный рычаг,
который давал прирост силы**: `qprior` против `search` — 55% против 45% на 600 партиях (§24).

**Круг §47 (модель как приор при бюджете времени) — механизм доведён, прироста нет.** Три вещи, которые
нужно знать про этот путь:

1. **Прежний приор в решении не участвовал.** Он входил добавкой `prior · log p` (`prior = 0,02`) к
   среднему по визитам. При бюджете 30 мс поиск успевает ~35 доигрываний на решение (`.workbuddy/
prior-probe.mjs`), то есть 5–7 визитов на вариант корня, — и добавка тонет в разбросе этих средних.
   Свип коэффициента от 0 до 30 результат не менял (22–26 побед из 48).
2. **Мнение модели в решении — это `rootAdvantages`** (`bot/play/search.js`): те же числа, что у ученика
   (`Q(s, a) + 0,8 · log1p(вес)`), но отсчитанные от лучшего варианта, поэтому приор расставляет варианты
   между собой, а не поднимает весь корень. В решение он входит с весом, **убывающим по визитам**
   (`SEARCH_PRIOR_MIX · advantage / (visits + SEARCH_PRIOR_TAU)`): пока статистики нет — решает модель,
   как только доигрываний накопилось — решает поиск. Тот же приор задаёт **порядок развёртывания**
   нераскрытых вариантов, а `SEARCH_TOP` позволяет сузить перебор до верхушки модели.
   `SEARCH_PRIOR_MIX=0` выключает всё это и возвращает прежний поиск — эталон замеров.
3. **Числа (§47).** Контроль `SEARCH_PRIOR_MIX=0` против себя — 50/50 (1196/1204 на 2 400 партиях),
   `mix = 0,8` — 48% против 52% (1151/1249); объединённо по сериям 51,9% против 48,1%. Модель как **лист**
   поиска (`qleaf`, `SEARCH_EVAL=qvalue`) — ровно 50/50 (716/724 на 1 440). Верхушка `SEARCH_TOP=3` — 47/48.
   То есть ни приор, ни верхушка, ни лист прироста не дают.

**Главный результат круга — не приор, а сам бюджет.** Все числа — шесть героев, 30 партий на пару,
лестница в обе стороны, 1 440 партий на замер, удержанные сиды 24001…24024:

| политика                    | против `qvalue` | против `greedy` | время замера |
| --------------------------- | --------------- | --------------- | ------------ |
| `qvalue` (живой ученик)     | —               | 54%             | 35 с         |
| `qprior` 30 мс, приор вкл.  | **57%**         | 66%             | 201 с        |
| `search` 30 мс, приор выкл. | **58%**         | —               | 220 с        |
| `turn` 200 мс (живой режим) | **65%**         | —               | 1 117 с      |
| `search` 200 мс             | **67%**         | **70%**         | 1 173 с      |

То есть доигрывания сильнее подсказки и сильнее самой модели: при 30 мс поиск берёт 57–58% у живого
ученика (приор при этом ничего не меняет: 57% против 58%), при бюджете браузера (200 мс) — 65–67%, а
против `greedy` — 70% против 54% у `qvalue`. Живой режим (`turn` при 200 мс) уже сильнее модели, поэтому
вопрос круга — не «включать ли поиск», а что даёт при том же бюджете больше приора.

### Ученик **не** считает вперёд сам

Признаки действия описывают одно действие; ни одна цель обучения не даёт ученику горизонта. Смотреть
вперёд умеет только поиск: оракул (32 доигрывания), `qprior` (поиск с подсказкой), политика `turn` (лист
на границе хода, §25) и планировщик цепочек `chain` (§25). Итог §25: горизонт не был узким местом —
`turn` против `search` 48%, `chain` против `search` 48%.

### Думать свой ход целиком — с лимитом времени

Сейчас «думанье» живёт в поиске, и у него есть **жёсткий предел времени**:

- `bot/play/search.js`: `SEARCH_TIME` (мс) — бюджет решения. Он режется **дважды**: между доигрываниями
  (цикл поиска) и **внутри** каждого доигрывания (`rolloutEnd` проверяет `deadline` на каждом шаге), иначе
  один длинный роллаут («мой ход плюс ответ») пересиживает бюджет;
- если время просили, лимит доигрываний снимается сам (`SEARCH_ITERATIONS` по умолчанию 32 — это ~50 мс);
  поиск возвращает `elapsed`, `timedOut` (сколько роллаутов срезала минутная стрелка) и `broken`
  (сорванные роллауты обязаны быть нулём);
- `turnEnd` + `replyTurn` — лист ставится не через `depth` шагов, а на границе **моего** хода и после
  ответа соперника. Вне своего хода (защита в чужом бою) границы нет, и поиск сам снимает `turnEnd`,
  иначе все варианты защиты получили бы одинаковую оценку;
- в браузере (`vs_ai`) ход считает `bot/play/ai.js: think` в бюджете `AI_TIME_MS` — **400 мс** (решение
  владельца §54, было 200), и **живым режимом с §51 является лист по глубине** (`turn: false` — политика
  `search`). Кроме времени счёта есть **пауза между действиями** (`AI_PAUSE_MS = 300`, §54): она не про
  силу, а про читаемость — с 200 мс бот мелькал, и несколько действий хода (маневр это клик на объявление
  плюс клик на каждый шаг) сливались в одно изменение доски; ноль отключает паузу, так считают ходы тесты и
  прогоны. Лист на границе хода остался переключателем (`--turn=1` в `think.js`, `turn: true` в вызове):
  **проба §29** показала, что при одинаковом бюджете времени ход целиком слабее обычного поиска (47% против
  53% на 1200 партиях, при 60 мс на решение), а **большие прогоны §51** (200 мс, шесть героев, 40 сидов,
  2 400 партий, лестница в обе стороны) дали паритет: `turn` против живого ученика — **67% против 33%**
  (1 613/787), `search` — **68% против 32%** (1 637/763); против простого бота `search` берёт **70%».
  **Почему бюджет поднят до 400 мс (§54):** при 200 мс поиск **не сходится** — ответ при 24 мирах совпадает
  с ответом при 96 лишь в 71% случаев, 48 миров — 79% (`.workbuddy/convergence-audit.mjs`, 2 147 решений), —
  а на 400 мс тот же поиск берёт против `greedy` **76% против 24%** (1 362/438 на 1 800 партиях) вместо 70%.
  Все механизмы «умнее распорядиться теми же 200 мс» отклоны замерами: приор (§47), парная оценка корня
  (§52), кэш повторных миров (§53, дал −28 п.п. и откачен), схлопывание одинаковых вариантов (§53, −6 п.п.),
  пул миров (§54, в шуме). Работает **лимит времени**, а не граница листа: `timeMs` режется и между
  роллаутами, и внутри каждого, поэтому ход не затягивается ни в одном режиме.

## 6. Шаг 5. Замер: честная приёмка

```powershell
node bot/tools/matrix.js --policy=qvalue --policy-b=greedy --games=20 --workers=12
node bot/tools/matrix.js --policy=qvalue --policy-b=search --games=10 --workers=12
$env:SEARCH_TIME=60; node bot/tools/matrix.js --policy=turn --policy-b=search --games=20 --workers=12
```

Правила замера (без них числа не значат ничего):

- **лестница в обе стороны**: политики меняются местами на той же серии сидов. Первый игрок сам по себе
  выигрывает 54–61%, поэтому односторонний замер показывает место, а не силу (`bot/tools/matchup.js:
firstSeatWins`, `ladderAggregateLine`);
- **парные сиды**: обе стороны играют один и тот же набор сидов;
- **объём**: на 600 партиях шум ±2 п.п., поэтому решение принимается на **≥1000 партиях**;
- **приёмка — ≥3 п.п.** к прежней версии. Артефакт, который не бьёт `greedy`, в игру не идёт.

## 7. Шаг 6. Разбор: `bot/tools/rank.js`

Винрейт говорит «сильнее или нет», а разбор — **почему**. Мера — доля пар вариантов внутри решения, где
порядок модели совпал с порядком цели (монетка 50%):

```powershell
node bot/tools/rank.js --data=trainer/data/oracle-c.jsonl.gz --target=value
node bot/tools/rank.js --data=trainer/data/oracle-c.jsonl.gz --target=value --limit=12000
```

Печатается: лучший вариант угадан, согласие по парам против случайной базы, **сожаление** (ценность
лучшего минус ценность сыгранного), доля решений с выбранным худшим вариантом и разрез по героям.

Две ловушки чтения, обе уже стоили неверных выводов:

1. **пара с равными оценками считается несогласием.** Если все варианты получили одну и ту же оценку,
   согласие падает к нулю — и это «модель слепа», а не «порядок перевёрнут». Ровно так выглядел провал
   клеток до блока 20..22 (§28);
2. **разрез по героям зависит от среза.** Герои входят в дневник партиями: на первых 6000 точках Медуза
   давала 26,9%, на 12 000 — около половины. Числа по героям читаются как «порядок величины», а не как
   рейтинг героев; сила героя меряется матрицей, а не этой мерой.

| операция                                 | цена (на этой машине)                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |

- numpy-тренер держит выборку в памяти: миллион точек не влезает (15 ГБ, своп) → `--limit` или torch;

- **размерность признаков действия вшита в артефакт**: после расширения признаков старые дневники и
  старые артефакты новыми числами не пользуются (старый артефакт грузится и играет, но блок 20..22 не
  читает — он короче на три числа).

## 11. Что дальше

- **признаки клетки** (сделано в круге §29): блок 20..22 снял слепоту к шагам — «все оценки равны» на
  решениях-клетках упало с 83,1% до 4,8%, общее согласие с оракулом выросло с 41,9% до 56,3%, но
  **оценивать** клетки модель ещё не умеет (40,5% при базе 50%) и силу это не подняло;
- **проверять цель, а не только ученика** (сделано в §29): согласие оракула с самим собой на повторных
  прогонах одной позиции — клетки 56–60%, карты 74–81%. Вывод: у клеток **в метках нет сигнала**, поэтому
  признаки к ним добавлять бессмысленно, пока цель не станет честнее. Инструменты для этого готовы и
  выключены по умолчанию: лист с геометрией (`SEARCH_EVAL=position`, политика `position`) и парная оценка
  корня (`pairedRootValues` — все варианты в одних мирах); на картах они дают 81% против 64%;
- **примесь мнения политики** — сделано по этому диагнозу и перемерено в §43 (`PRIOR_MIX` 0,3 → **0,8**):
  `qvalue` против `greedy` 53–54% → **55%**; правило политики на текущем артефакте сильнее модели в её
  области, поэтому уточнение самих правил (шесть генов §43) игру не двигает — двигает их доля в решении;
- **следующий круг — дневник с честным оракулом** (сделан и не взят, §46: честные метки вдвое меньше
  шумят, но сила та же — 53% против 53%); **шум меток, объём и лучший учитель — не узкое место**;
- **ценность хода внутри поиска** — проверено в §47 и **не работает**: приор корня (`qprior`) теперь
  действительно доходит до решения (`rootAdvantages`), но даёт 48% против 52% у того же поиска без приора;
  модель как лист поиска (`qleaf`) — ровно 50/50. Зато **бюджет доигрываний работает**: поиск при 30 мс
  берёт 57% у живого ученика, при 200 мс — 67%, против `greedy` — 70% против 54%. Дальше вопрос не «как
  подсказать поиску», а «тянет ли браузер 200 мс на действие» и «что даёт больше при том же бюджете»;
- **шумность ценностей оракула**: 32 доигрывания в детерминизированных мирах дают оценку варианта с
  разбросом — проверять большим бюджетом (96) и повторными прогонами одной позиции. Для соседних клеток
  этот шум и есть причина, по которой «какая из двух лучше» не выучивается;
- не повторять: свои партии как источник цели для линейной модели пары «состояние + действие» (§26),
  доли доигрываний как цель (§24), «повтори выбор учителя» (§24), лист на границе хода как способ
  «думать ход» (§29: 47% против 53% при равном времени).
